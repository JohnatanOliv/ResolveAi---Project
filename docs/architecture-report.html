Arquitetura
do ResolveAi

Aplicação de gestão de ocorrências com frontend React, API Express, PostgreSQL no Neon e controle administrativo de acesso.

Frontend: React + ViteBackend: Node.js + ExpressDados: PostgreSQL

Visão baseada na configuração do repositório e nos alvos Docker documentados.

01 / Produção

Arquitetura publicada

No ambiente publicado, frontend e API são serviços separados no Render. O navegador acessa ambos por HTTPS. A API é a única camada que conecta ao banco PostgreSQL gerenciado no Neon.

Frontend estático servido pelo Render.
API autentica, autoriza e aplica regras de negócio.
Neon é serviço gerenciado externo; credenciais ficam em segredo de ambiente.
Chamadas HTTPS/TLS atravessam fronteira de rede.
Importante: em produção no Render, o navegador chama diretamente a URL pública da API. O proxy Nginx pertence ao Compose local e não faz parte deste desenho.
02 / Desenvolvimento

Docker Compose local

As imagens de produção têm dois alvos. O container Nginx serve o bundle compilado do React e encaminha chamadas da API pela rede privada do Compose. O container Node acessa o Neon externo usando variáveis de ambiente.

Imagem API

Node 22, dependências de runtime e código TypeScript compilado. Testes executam no estágio de build.

Imagem web

Bundle Vite compilado em build stage e servido por Nginx Alpine.

Persistência

Não existe banco PostgreSQL no Compose. O banco continua no Neon; não há volume local de dados.

Limite de confiança: tráfego do navegador termina no Nginx local. Nginx → API usa rede interna do Compose; API → Neon sai pela rede usando TLS.
03 / Fluxos

Cadastro e autenticação

O papel enviado pelo cliente não é usado para promover uma conta. O serviço cria registros públicos como SOLICITANTE; login valida a senha e emite um JWT.

Credenciais: a senha armazenada é hash bcrypt. O JWT é retornado ao cliente e usado como Bearer nas rotas protegidas.
04 / Governança

Pedido e aprovação de gestor

O fluxo de gestão tem duas barreiras: o solicitante autenticado abre o pedido; apenas um usuário ADMIN autenticado pode consultar a fila e decidir. A promoção para GESTOR ocorre dentro da mesma transação que registra a decisão.

Dados relevantes

manager_access_requests guarda solicitante, justificativa, status, decisão, administrador e datas. Um índice parcial impede pedidos pendentes duplicados por usuário.

Bootstrap do primeiro ADMIN

A conta inicial é promovida manualmente no banco por uma operação administrativa controlada. Não existe rota pública para criar ADMIN.

05 / Ciclo de vida

Estados da ocorrência

O fluxo abaixo corresponde às transições aceitas pela camada de serviço. Resolvida e Cancelada são estados terminais; cada transição exige observação e registra ator/data no histórico.

Regras: ABERTA → EM ANÁLISE → EM ATENDIMENTO → RESOLVIDA. O cancelamento pode ocorrer antes da conclusão. Estados terminais não reabrem pelo fluxo atual.
06 / Dados e controles

Modelo de domínio

Gestores cadastram empresas e endereços curtos; solicitantes escolhem a empresa e o prédio ao abrir uma ocorrência. A chave composta garante que o endereço pertence à empresa. As entidades preservam histórico, atribuição e avaliação.
